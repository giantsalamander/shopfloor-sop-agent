## 二、智能体本地部署步骤（全部本地算力，数据不出机）

### 2.1 模型服务（vLLM 0.29.0，venv ~/envs/vllm）

**关键陷阱（实测）**：vLLM 必须从登录 shell 启动——/etc/profile.d/nv_paths.sh 只在登录 shell 把 /usr/local/cuda/bin 注入 PATH，缺失时 FlashInfer 运行时检查失败（报 FlashInfer backend is not available，即使 flashinfer 0.6.18 已安装且原版服务就是 FlashInfer 后端跑的）。run-*.sh 脚本已内置 PATH 兜底。

```bash
# Nemotron（文本/推理/编排主力，:8000）
~/run-nemotron.sh
# 等价命令：
vllm serve ~/models/Nemotron-3.5-Lightning-30B-A3B-NVFP4 \
  --served-model-name nemotron --max-model-len 65536 \
  --gpu-memory-utilization 0.9 --trust-remote-code

# Step3-VL（图文识别，:8001，与 Nemotron 互斥）
~/run-step3vl.sh
# 等价命令：
vllm serve ~/models/Step3-VL-10B \
  --served-model-name step3vl --port 8001 --max-model-len 32768 \
  --gpu-memory-utilization 0.9 --trust-remote-code \
  --limit-mm-per-prompt '{"image": 16}'
# 注意 --limit-mm-per-prompt 必须是 JSON 格式，vLLM 0.29 不接受 key=value 写法
```

**互斥切换设计**：128GB 统一内存无法同时容纳两个 0.9 利用率实例（约 109GB + 19GB + 系统开销）。run-*.sh 内置互斥逻辑：起一个自动停另一个，切换耗时 4-5 分钟（模型加载）。四个脚本：run-nemotron.sh / stop-nemotron.sh / run-step3vl.sh / stop-step3vl.sh，均带就绪探测循环与失败提示。

## 三、大模型优化（实测有效）

1. **NVFP4 权重量化（NVIDIA ModelOpt）**：Nemotron 官方 NVFP4 版在 Blackwell 上走 Marlin NVFP4 MoE kernel，30B 模型权重仅约 15-18GB，为 65536 上下文的 fp8 KV cache 腾出空间。
2. **fp8_e4m3 KV cache**：vLLM 自动启用（启动日志 kv_cache_dtype=fp8_e4m3），长上下文显存减半。
3. **FlashInfer attention + DeepGEMM**：vLLM 0.29 在 GB10 上自动选择（启动日志 Using FLASHINFER attention backend / DeepGEMM PDL enabled），依赖登录 shell 的 CUDA PATH（见 2.1 陷阱）。
4. **max_model_len 调优**：32768→65536 实测可行（模型原生支持 1M）；更大值需验证 KV cache 块容量。
5. **结构化输出（本项目最重要的模型侧结论）**：response_format={"type":"json_object"} 对 Nemotron 与 Step3-VL 两个推理模型都有效，token 级强制合法 JSON；extra_body guided_json 对 Step3-VL 无效（实测仍输出思考链）。推理模型别指望 prompt 约束"只输出 JSON"。
6. **gpu-memory-utilization 0.9**：统一内存架构下给系统/Ollama 留约 12GB 余量。

## 四、Agent Skills 设计

### 4.1 设计原则
- **模型管理解，工具管事实**：数值判定（公差、校准期、危险类别）全部放确定性 Python 工具，模型只产 JSON 意图与根因注释——合规判定可复现、可审计。
- **双格式 spec**：每个 skill 同时导出 OpenAI function spec（编排器用）与 Bedrock toolSpec（对齐 SOP-Bench 评测协议），一份实现两份接口（tools.py 的 TOOLS_OPENAI / TOOLSPEC_BEDROCK）。
- **统一 dispatch**：tools.call_tool(name, **kwargs) 单一入口，异常包装为 {"error":...} 不炸流水线。
- **纯函数无副作用**：工具不内嵌模型调用（视觉/文本抽取在 pipeline 层完成后以参数传入），可单测。

### 4.2 Skill 清单与流水线挂载点

| # | Skill | 挂载步骤 | 输入 → 输出 |
|---|---|---|---|
| 1 | std-doc-parse | StdParse | sop_text → 条款/阈值/设备/安全要点 |
| 2 | pid-or-wiring-ocr | StdParse | Step3-VL 接线图 JSON → 设备/端口/设定值 |
| 3 | sop-graph-builder | SOPPlanner | 步骤+视觉 → 有向图(节点/边/安全门) |
| 4 | instrument-validator | InstrumentCheck | SN+需求 → 型号/量程/校准期校验 |
| 5 | worker-form-schema | WorkerExecute | SOP图 → 回传表单模板 |
| 6 | photo-evidence-check | Validate | 面板读数 JSON+表单 → 交叉校验 |
| 7 | tolerance-calc | Validate | 实测/设定/公差 → 偏差%+合格判定 |
| 8 | regulatory-rule | Validate | SDS/产品ID → 危险类/闪点/包装组 |
| 9 | nonconformance | ComplianceJudge | finding → 分级+回退建议 |
| 10 | audit-report | Reporter | findings+trace → 三版报告 |

详细说明见 docs/skills/<name>.md（10 个 markdown 文件）。

### 4.3 可恢复设计
- checkpoint：checkpoints/<batch_id>/<step>.json（含输入输出与工具调用记录）。
- 回退：pipeline.run(batch_id, resume_from="validate") 从任意步重跑，前序步骤从 checkpoint 恢复上下文。
- 触发规则：nonconformance 工具给出 rerun_phase（EvidenceParse=重识图 / SOPPlanner=重拆步骤），Gradio"从某步重跑"下拉直接映射。
