# 项目说明（作品特点 / 核心亮点 / 技术方案 / 架构 / 优化）

## 一、作品定位

ShopFloor SOP Agent 是一个跑在 NVIDIA DGX Spark 上的**本地化 SOP 合规检查智能体**，面向工厂设备点检、实验室仪器校准、危化品收货三类场景。它解决的不是"模型问答 SOP"，而是把一条真实业务闭环搬进单机：**标准文档进系统 → 自动拆解为可执行步骤 → 视觉校验仪器与现场 → 工人按步回传记录 → 系统用确定性工具判定合格/不合格 → 不合规可回退重做 → 产出带引用、带 trace 的可审计合规报告**。

作品由两个本地大模型驱动，分工明确：NVIDIA Nemotron-3.5-Lightning-30B-A3B-NVFP4 负责长文本理解与决策（标准条款抽取、SOP 步骤图规划、合规判定、报告生成），阶跃星辰 Step3-VL-10B 负责图文识别（仪器面板读数、警示符号、现场照片结构化）。全部推理在 DGX Spark 的 128GB 统一内存上完成，标准文档、工人记录、现场照片**全程不出机**，天然满足工厂数据保密要求。

核心亮点有六个。其一，**统一内存双模型调度**：128GB 装不下两个满载 vLLM 实例，我们设计"互斥切换 + 视觉预缓存"两阶段架构，视觉解析离线批量完成，在线判定只依赖文本模型，演示零等待。其二，**不依赖模型原生 tool calling**：实测 Nemotron 输出伪 XML 工具调用而非结构化 tool_use，我们改用 Python 驱动编排——模型只产 JSON 意图，工具由编排器确定性调用，判定 100% 可复现。其三，**推理模型结构化输出修复**：实测 guided_json 对 VLM 无效，改用 response_format json_object 强制合法 JSON，视觉字段抽取成功率从 2/4 提升到 4/4。其四，**可恢复工作流**：10 步流水线每步落 checkpoint，失败可从任意步重跑，人工复核后局部重算而非全量重来。其五，**客观评测对齐**：工具规格同时导出 OpenAI function 与 Bedrock toolSpec 双格式，直接对齐 SOP-Bench（amazon/sop-bench）评测协议。其六，**视觉不止读数**：Step3-VL 在超量程面板上识别出红色三角告警图标并触发交叉校验，证明多模态证据链能发现表单之外的现场异常。

实测效果（reports/B9db05c.json，Gradio UI 实跑）：4 条工人回传中，校准过期仪器（2026-08-27）与单位错误（12400mV 当 12V 报，偏差 103233%）两条被准确判 FAIL 并给出根因，合格两条判 PASS，审计 trace 12 条全程可追溯。

## 二、技术实现方案

### 2.1 分层架构
- **模型层**：vLLM 0.29.0 双实例（互斥）。Nemotron :8000（NVFP4 权重、fp8_e4m3 KV cache、FlashInfer attention、Marlin NVFP4 MoE kernel、max_model_len 65536）；Step3-VL :8001（bf16、--limit-mm-per-prompt image=16 JSON 格式、max_model_len 32768）。
- **客户端层**（clients.py）：OpenAI SDK 直连两个 vLLM 端点；nemotron_json / step3vl_image_json 统一走 response_format json_object 强制 JSON；_strip_reasoning 兜底剥离思考链。
- **技能层**（tools.py）：10 个确定性 Python 工具（查资产库/算公差/规则匹配/报告组装），每个导出 OpenAI function spec + Bedrock toolSpec 双格式。
- **编排层**（pipeline.py）：10 步流水线 Ingest→StdParse→SOPPlanner→InstrumentCheck→WorkerExecute→EvidenceParse→Validate→ComplianceJudge→Reporter→HumanReview；每步写 checkpoints/<batch>/<step>.json；run(batch_id, resume_from=step) 支持回退重跑；模型切换钩子 ensure_nemotron()/ensure_step3vl() 调 run-*.sh。
- **交互层**（app.py）：Gradio 单页——上传标准/回传 → 快速判定（预缓存视觉）或全流程（实时切换）→ findings 表 + 三版报告 + 审计 trace + "从某步重跑"。

### 2.2 关键数据契约（schemas.py, pydantic v2）
- InstrumentPanelReading：panel_type/brand/model/range/setpoint/measured/unit/step_id/warnings/missing/bbox——Step3-VL 的输出契约。
- WorkerFormRow：step_id/param/setpoint/measured/unit/instrument_sn/timestamp/photo_path。
- SOPStep/SOPGraph：节点(步骤)+边(依赖/分支)+安全门。
- ComplianceFinding/ComplianceReport：pass/fail/marginal + 条款引用 + 页码 + bbox + 根因 + audit_trace。

### 2.3 判定逻辑（确定性优先）
Validate 步的判定顺序：仪器校验失败(instrument_validator) → FAIL；公差超界(tolerance_calc) → FAIL；数据缺失 → MARGINAL；视觉交叉校验不符(photo_evidence_check) → MARGINAL；否则 PASS。ComplianceJudge 再让 Nemotron 复核 findings 并补根因/条款引用——模型只"加注释"，不推翻确定性工具的结论。

## 三、优化方案（已实施）

1. **结构化输出**：response_format json_object 替代 prompt 约束与 guided_json（后者对 VLM 无效，实测）。
2. **视觉预缓存**：prep_vision.py 离线批量解析 + fix_vision_cache.py 修复历史缓存，在线零视觉调用。
3. **上下文预算**：Nemotron max_model_len 32768→65536（模型原生 1M，KV cache 按 0.9 显存利用率自适应）。
4. **启动环境**：vLLM 必须登录 shell 启动（/etc/profile.d/nv_paths.sh 注入 /usr/local/cuda/bin），否则 FlashInfer 运行时检查失败——已固化进 run-*.sh 脚本。
5. **checkpoint 粒度**：按流水线步而非按请求，回退成本=单步重跑。
